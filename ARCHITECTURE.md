# Cherry Engine Architecture

## Boundary

CherryBrowser owns the web-platform-facing engine layers:

- HTML parsing and DOM construction
- CSS parsing, selector matching and cascade
- style computation
- layout
- display-list generation
- hit testing
- navigation policy
- future JavaScript runtime and DOM bindings
- future compositor and process isolation

Generic infrastructure libraries are allowed for TLS, HTTP framing, cryptography, OS windows, graphics APIs, image codecs, fonts and compression.

## Long-term process model

```text
+---------------- Browser Process ----------------+
| tabs | history | permissions | downloads | UI  |
+----------------------+---------------------------+
                       |
                       | IPC
                       v
+--------------- Renderer Process ----------------+
| DOM | CSS | JS VM | Style | Layout | Paint      |
+----------------------+---------------------------+
                       |
                       | display lists / surfaces
                       v
+-------------- Compositor Process ---------------+
| GPU resources | raster | layers | compositing   |
+--------------------------------------------------+

Network and storage services become isolated processes after the
single-process engine is functionally mature.
```

## Current 0.1 pipeline

```text
reqwest transport
    -> Cherry HTML parser
    -> Cherry DOM
    -> Cherry CSS parser/cascade
    -> Cherry block/inline flow layout
    -> Cherry display list
    -> egui/Glow native presentation shell
```

The egui/Glow layer is a presentation shell, not the web renderer. Layout coordinates,
paint items, link hit regions, DOM and CSS semantics are generated by Cherry code.
The shell can therefore be replaced later by a dedicated wgpu/Vulkan/Metal/D3D compositor
without replacing the browser engine.
